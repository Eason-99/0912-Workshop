\section{Step 1：从 LLM API 开始}

\begin{outlinebox}
这一部分主要展示：

\begin{enumerate}
    \item API（Application Programming Interface，应用程序接口）是什么；
    \item 一次 LLM 调用发生了什么；
    \item Prompt、Message、Response 的关系；
    \item 一个最简单的 Python Demo；
    \item 为什么单次 API 调用无法完成复杂任务。
\end{enumerate}
\end{outlinebox}

\subsection{把 LLM 看成一个函数}

从程序角度，可以先非常粗略地把 LLM 理解成：

\[
\text{response}
=
\text{LLM}(\text{prompt})
\]

也就是：

\[
\text{输入文本}
\rightarrow
\text{模型}
\rightarrow
\text{输出文本}
\]

例如：

\begin{lstlisting}[language=Python]
question = """
Explain the difference between
Poisson and Normal distributions.
"""

response = call_llm(question)

print(response)
\end{lstlisting}

实际使用中，模型通常接收的不只是一个字符串，而是一组
Message（消息）。

例如：

\begin{lstlisting}[language=Python]
messages = [
    {
        "role": "system",
        "content": "You are a research assistant."
    },
    {
        "role": "user",
        "content": "Compare three LLM agent papers."
    }
]
\end{lstlisting}

模型看到的内容可以粗略写成：

\[
\text{Instruction}
+
\text{Context}
+
\text{User Query}
\]

然后生成 Response（响应）。

\subsection{现实中的例子}

常见的 LLM API 提供者包括：

\begin{itemize}
    \item OpenAI；
    \item Anthropic Claude；
    \item Google Gemini；
    \item DeepSeek；
    \item 开源模型服务，例如基于 vLLM 部署的模型。
\end{itemize}

这些 API 的参数形式可能不同，
但是核心模式基本一致：

\[
\text{程序发送请求}
\rightarrow
\text{模型生成}
\rightarrow
\text{程序收到结果}
\]

\subsection{Demo 1：最简单的一次 API 调用}

可以现场让模型完成：

\begin{center}
\texttt{What is 8173 * 9271?}
\end{center}

示意代码：

\begin{lstlisting}[language=Python]
question = "What is 8173 * 9271?"

response = call_llm(question)

print(response)
\end{lstlisting}

然后提出问题：

\begin{center}
\textbf{模型是真的调用了一个计算器吗？}
\end{center}

通常答案是否定的。

如果只是普通文本生成，
模型本质上还是在生成 Token（词元）。

\begin{keybox}
普通 API 调用的本质仍然是：

\[
\text{Input}
\rightarrow
\text{LLM}
\rightarrow
\text{Output}
\]

模型还没有真正与外部世界产生交互。
\end{keybox}

\begin{notebox}
这一部分不要深入讲 Transformer、Attention 或 Sampling。

Workshop 的重点是 Agent System（智能体系统），
不是语言模型原理。

Temperature（温度参数）等也只需一两句话带过。

关键是让听众知道：
后面所有复杂 Agent，本质上都建立在这种普通 API 调用之上。
\end{notebox}

\section{Step 2：Structured Output——让模型输出“决策”}

\begin{outlinebox}
这一部分主要展示：

\begin{enumerate}
    \item 为什么自然语言输出不利于程序控制；
    \item JSON（JavaScript Object Notation）形式；
    \item Action（动作）与 Arguments（参数）；
    \item LLM 从 Text Generator 向 Decision Module 转变。
\end{enumerate}
\end{outlinebox}

假设模型输出：

\begin{lstlisting}
I think we should use a calculator.
\end{lstlisting}

人类当然知道它是什么意思，
但程序很难稳定解析。

因此可以要求模型输出 Structured Output（结构化输出）。

例如：

\begin{lstlisting}
{
    "action": "calculator",
    "arguments": {
        "expression": "8173 * 9271"
    }
}
\end{lstlisting}

此时程序可以直接读取：

\begin{lstlisting}[language=Python]
action = response["action"]
arguments = response["arguments"]
\end{lstlisting}

于是 LLM 的作用开始发生变化。

原来：

\[
\text{LLM}
\rightarrow
\text{Natural Language Answer}
\]

现在：

\[
\text{LLM}
\rightarrow
\text{Machine-readable Decision}
\]

即：

\[
\text{文本生成器}
\rightarrow
\text{决策模块}
\]

\subsection{Demo 2：选择 Calculator}

Prompt 可以告诉模型：

\begin{lstlisting}
If arithmetic calculation is required,
return a JSON object:

{
    "action": "calculator",
    "expression": "..."
}
\end{lstlisting}

用户输入：

\begin{lstlisting}
What is 8173 * 9271?
\end{lstlisting}

模型输出：

\begin{lstlisting}
{
    "action": "calculator",
    "expression": "8173 * 9271"
}
\end{lstlisting}

\begin{notebox}
需要强调：

Structured Output 本身还不是 Agent。

它只是解决了一个很重要的问题：

\[
\text{如何让程序可靠理解 LLM 的决定？}
\]

现代 API 中通常可以通过 JSON Schema（JSON 模式）
或 Function Schema（函数模式）
对模型输出进行进一步约束。
\end{notebox}

\section{Step 3：Tool Calling——让 LLM 能够采取行动}

\begin{outlinebox}
这一部分主要展示：

\begin{enumerate}
    \item Tool（工具）是什么；
    \item LLM 与 Runtime（运行环境）的分工；
    \item Claude、ChatGPT 等工具型能力；
    \item Calculator Tool Demo；
    \item Tool Calling 的完整执行链。
\end{enumerate}
\end{outlinebox}

\subsection{Tool Calling 的核心机制}

假设我们定义一个工具：

\begin{lstlisting}[language=Python]
def calculator(expression):
    return eval(expression)
\end{lstlisting}

为了教学，可以先忽略安全问题。

模型可以得到工具说明：

\begin{lstlisting}
Tool:
calculator(expression)

Use it for arithmetic calculations.
\end{lstlisting}

然后模型产生：

\begin{lstlisting}
{
    "tool": "calculator",
    "arguments": {
        "expression": "8173 * 9271"
    }
}
\end{lstlisting}

但这里最重要的一点是：

\begin{center}
\textbf{LLM 并没有真正执行 Python 函数。}
\end{center}

真正执行工具的是外部程序。

\subsection{完整执行流程}

\begin{center}

\begin{tikzpicture}[node distance=0.7cm]

\node[box] (user) {User};
\node[box, right=of user] (llm1) {LLM};
\node[box, right=of llm1] (call) {Tool Call};

\node[box, below=1cm of call] (runtime)
{Runtime};

\node[box, left=of runtime] (result)
{Tool Result};

\node[box, left=of result] (llm2)
{LLM Again};

\draw[arrow] (user) -- (llm1);
\draw[arrow] (llm1) -- (call);
\draw[arrow] (call) -- (runtime);
\draw[arrow] (runtime) -- (result);
\draw[arrow] (result) -- (llm2);

\end{tikzpicture}

\end{center}

也就是：

\[
\text{User}
\rightarrow
\text{LLM}
\rightarrow
\text{Tool Call}
\rightarrow
\text{Runtime}
\]

然后：

\[
\text{Tool Result}
\rightarrow
\text{LLM}
\rightarrow
\text{Answer}
\]

\subsection{Tool 可以是什么？}

对于 LLM 来说，下列东西本质上都可以抽象为 Tool：

\begin{itemize}
    \item Calculator（计算器）；
    \item Web Search（网页搜索）；
    \item Python；
    \item Database Query（数据库查询）；
    \item Browser（浏览器）；
    \item File System（文件系统）；
    \item Email API；
    \item Calendar API。
\end{itemize}

科研环境中的 Tool 还可以包括：

\begin{itemize}
    \item Search Paper；
    \item Read PDF；
    \item Run Experiment；
    \item Parse Log；
    \item Plot Figure；
    \item Edit \LaTeX；
    \item Run Unit Test。
\end{itemize}

\subsection{现实产品例子}

Claude、ChatGPT 等现代 LLM 产品都可以在不同环境中表现出
Tool-augmented（工具增强）能力，例如：

\begin{itemize}
    \item 搜索网页；
    \item 执行代码；
    \item 读取文件；
    \item 操作外部服务。
\end{itemize}

但需要注意：

\begin{center}
\textbf{不要根据网页 UI 推断产品内部的具体实现架构。}
\end{center}

我们能观察到的是功能行为，
而具体内部编排可能是 Workflow、Agent，
也可能是多个机制组合。

\begin{notebox}
现场 Demo 建议使用 Calculator。

原因是：

\begin{itemize}
    \item 无网络依赖；
    \item 结果确定；
    \item Tool Result 容易理解；
    \item 能清楚展示 LLM 与 Runtime 的职责分工。
\end{itemize}

另外：

\texttt{eval()} 不适合真实系统中的不可信输入。

真实系统需要输入验证（Input Validation）、
权限限制（Permission Control）和 Sandbox（沙箱）。
\end{notebox}

% ============================================================
% 5. Workflow
% ============================================================

\section{Step 4：Workflow——把多个 LLM 和 Tool 串起来}

\begin{outlinebox}
这一部分主要展示：

\begin{enumerate}
    \item 什么是 Workflow（工作流）；
    \item 多步骤任务；
    \item AI Writing 与 PPT 生成的 Workflow；
    \item Workflow 为什么还不一定是 Agent。
\end{enumerate}
\end{outlinebox}

假设要完成一个 Literature Review（文献综述）。

可以提前写死：

\[
\text{Search}
\rightarrow
\text{Read}
\rightarrow
\text{Extract}
\rightarrow
\text{Summarize}
\]

这种流程就是 Workflow。

\begin{center}

\begin{tikzpicture}[node distance=0.55cm]

\node[smallbox] (q) {Research Question};
\node[smallbox, right=of q] (s) {Search};
\node[smallbox, right=of s] (r) {Read};
\node[smallbox, right=of r] (e) {Extract};
\node[smallbox, right=of e] (w) {Write};

\draw[arrow] (q) -- (s);
\draw[arrow] (s) -- (r);
\draw[arrow] (r) -- (e);
\draw[arrow] (e) -- (w);

\end{tikzpicture}

\end{center}

Workflow 的特点：

\begin{itemize}
    \item 路径预先确定；
    \item 易于 Debug（调试）；
    \item 成本比较可预测；
    \item 行为稳定；
    \item 但适应性较弱。
\end{itemize}

\subsection{AI Writing 的 Workflow}

例如：

\[
\text{Topic}
\rightarrow
\text{Search References}
\rightarrow
\text{Outline}
\rightarrow
\text{Draft}
\rightarrow
\text{Check}
\rightarrow
\text{Revise}
\]

这已经比单次 Prompt 强很多。

\subsection{AI PPT 的 Workflow}

类似：

\[
\text{Topic}
\rightarrow
\text{Outline}
\rightarrow
\text{Generate Slides}
\rightarrow
\text{Generate Figures}
\rightarrow
\text{Layout Check}
\rightarrow
\text{Revise}
\]

因此很多所谓“AI 自动做 PPT”的系统，
从架构上其实完全可以是 Workflow。

\begin{keybox}
Workflow 和 Agent 的关键区别，不在于系统有没有很多步骤。

真正的问题是：

\[
\boxed{\text{下一步动作是谁决定的？}}
\]
\end{keybox}

\begin{notebox}
这里不要贬低 Workflow。

实际工程里，如果流程本来就非常明确，
Workflow 往往比完全自主 Agent 更稳定、更便宜。

“Agent 化”不是越多越好。
\end{notebox}

% ============================================================
% 6. Agent Loop
% ============================================================

\section{Step 5：Agent Loop——真正进入 Agent}

\begin{outlinebox}
这一部分是整个 Workshop 的核心。

主要展示：

\begin{enumerate}
    \item Workflow 与 Agent 的根本区别；
    \item State（状态）与 Action（动作）；
    \item Agent Loop（智能体循环）；
    \item Observe--Reason--Act；
    \item 最小 Agent 代码；
    \item Research Agent Demo。
\end{enumerate}
\end{outlinebox}

\subsection{Workflow 与 Agent}

Workflow 中：

\[
A
\rightarrow
B
\rightarrow
C
\]

下一步由程序员预先确定。

Agent 中，
模型根据当前状态 \(s_t\)
动态选择动作 \(a_t\)。

可以写成：

\[
a_t = \pi(s_t)
\]

其中：

\begin{itemize}
    \item \(s_t\)：State（状态）；
    \item \(a_t\)：Action（动作）；
    \item \(\pi\)：Policy（策略），
    \(\pi\) 读作 \textbf{pi（派）}。
\end{itemize}

这里与 Reinforcement Learning（强化学习）的形式很像，
但不应该说两者完全等价。

\subsection{Agent Loop}

Agent 可以抽象成：

\[
\text{Observe}
\rightarrow
\text{Reason}
\rightarrow
\text{Act}
\rightarrow
\text{Observe}
\rightarrow
\cdots
\]

示意图如下。

\begin{center}

\begin{tikzpicture}[node distance=1cm]

\node[box] (observe) {Observe\\观察};
\node[box, right=of observe] (reason) {Reason\\判断};
\node[box, right=of reason] (act) {Act\\行动};

\node[box, below=1cm of reason] (env)
{Environment\\环境};

\draw[arrow] (observe) -- (reason);
\draw[arrow] (reason) -- (act);
\draw[arrow] (act) -- (env);
\draw[arrow] (env) -| (observe);

\end{tikzpicture}

\end{center}

\subsection{最小 Agent 代码}

一个非常简化的 Agent 可以写成：

\begin{lstlisting}[language=Python]
messages = [user_query]

for step in range(MAX_STEPS):

    response = call_llm(
        messages,
        tools=tools
    )

    if response.type == "final":
        return response.answer

    if response.type == "tool_call":

        result = execute_tool(
            response.tool,
            response.arguments
        )

        messages.append(response)
        messages.append(result)
\end{lstlisting}

核心逻辑只有：

\begin{lstlisting}[language=Python]
while not done:

    state = observe()

    action = llm(state)

    observation = execute(action)

    update_state(observation)
\end{lstlisting}

\begin{keybox}
Agent Framework 最核心的部分并不神秘：

\[
\boxed{
\text{LLM}
\rightarrow
\text{Action}
\rightarrow
\text{Observation}
\rightarrow
\text{LLM Again}
}
\]

也就是一个循环。
\end{keybox}

% 7. Research Agent
% ============================================================

\section{Demo：从 Workflow 到 Research Agent}

\begin{outlinebox}
这一部分建议做成 Workshop 中最重要的现场 Demo。

任务：

\begin{quote}
Find representative papers about
LLM agent planning and compare their main ideas.
\end{quote}

展示的重点不是最终答案质量，
而是 Agent 如何根据 Observation 动态决定下一步。
\end{outlinebox}

可用 Tool：

\begin{lstlisting}[language=Python]
search_paper(query)

read_paper(paper_id)

save_note(content)
\end{lstlisting}

第一次：

\[
\text{Action}
=
\text{Search Paper}
\]

得到若干结果。

Agent 判断：

\begin{quote}
当前结果主要集中在 reasoning，
planning 相关工作不足。
\end{quote}

于是再次：

\[
\text{Action}
=
\text{Search Again}
\]

然后：

\[
\text{Read Paper A}
\rightarrow
\text{Read Paper B}
\]

接着 Agent 判断信息仍然缺少 evaluation 部分，
再次搜索。

整个执行轨迹（Trajectory）可能变成：

\[
\begin{aligned}
&\text{Search} \\
\rightarrow\;& \text{Read A} \\
\rightarrow\;& \text{Read B} \\
\rightarrow\;& \text{Search Again} \\
\rightarrow\;& \text{Read C} \\
\rightarrow\;& \text{Summarize}
\end{aligned}
\]

这时和固定 Workflow 的区别就非常明显。

固定 Workflow：

\[
\text{Search once}
\rightarrow
\text{Read}
\rightarrow
\text{Write}
\]

Agent：

\[
\text{根据结果决定是否再次 Search}
\]

\begin{notebox}
如果现场网络不稳定，
建议不要真正实时访问 Scholar 或其他网站。

可以提前准备一个 Mock Tool（模拟工具），
例如：

\begin{lstlisting}[language=Python]
def search_paper(query):
    return mock_database[query]
\end{lstlisting}

这样既能展示 Agent Loop，
又不会因为网络问题翻车。
\end{notebox}

\section{ChatGPT、Claude、DeepSeek 网页版是不是 Agent？}

这也是 Workshop 中非常容易被问到的问题。

关键不是看 UI（用户界面），
而是看内部任务执行行为。

\begin{center}
\begin{tabular}{p{0.43\textwidth}p{0.43\textwidth}}
\toprule
行为 & 更合理的理解 \\
\midrule

User $\rightarrow$ LLM $\rightarrow$ Answer
&
普通 LLM Application
\\

Search $\rightarrow$ Retrieve $\rightarrow$ Generate
且流程固定
&
Workflow
\\

模型自己决定是否搜索、执行代码或读取文件
&
Agentic Behavior
\\

模型反复调用工具，直到认为任务完成
&
典型 Agent Loop
\\

\bottomrule
\end{tabular}
\end{center}

因此，更准确的说法是：

\begin{quote}
一个现代聊天产品可能同时包含
普通 LLM 调用、Workflow 和 Agentic Execution
（智能体式执行）。
\end{quote}

不能简单说：

\begin{quote}
“网页版 ChatGPT 就一定是一个 Agent。”
\end{quote}

\begin{notebox}
产品内部架构通常不是公开透明的，
而且会不断变化。

演讲时只讨论公开能力和可观察行为，
不要断言某个商业产品内部一定使用某种具体 Agent Loop。
\end{notebox}

% 9. State Memory
% ============================================================

\section{Step 6：State 与 Memory}

\begin{outlinebox}
这一部分展示：

\begin{enumerate}
    \item Context（上下文）；
    \item State（状态）；
    \item Working Memory（工作记忆）；
    \item Long-term Memory（长期记忆）；
    \item Retrieval（检索）；
    \item 为什么不能把所有历史全部塞进 Prompt。
\end{enumerate}
\end{outlinebox}

\subsection{Context}

Context 是模型在某一次调用时实际能够看到的信息。

例如：

\[
\text{System Prompt}
+
\text{User Query}
+
\text{Tool Results}
+
\text{History}
\]

\subsection{State}

State 是 Agent 当前任务的结构化状态。

例如：

\begin{lstlisting}[language=Python]
state = {
    "goal": "survey LLM agents",
    "papers_found": 12,
    "papers_read": 5,
    "remaining_questions": [
        "planning",
        "evaluation"
    ]
}
\end{lstlisting}

\subsection{Working Memory}

Working Memory（工作记忆）
保存当前任务执行过程中暂时需要的信息。

例如：

\begin{itemize}
    \item 已经读过哪些论文；
    \item 当前总结；
    \item 尚未解决的问题；
    \item 当前 Plan。
\end{itemize}

\subsection{Long-term Memory}

Long-term Memory（长期记忆）
通常意味着信息持久保存在外部系统中，例如：

\begin{itemize}
    \item Database；
    \item Vector Database（向量数据库）；
    \item File System；
    \item Knowledge Base。
\end{itemize}

需要特别注意：

\begin{center}
\textbf{Vector Database 不等于 Memory 本身。}
\end{center}

它只是实现长期信息存储和 Retrieval 的一种方式。

\subsection{为什么不能无限扩大 Context？}

随着 Agent 执行：

\[
\text{History} \uparrow
\]

通常伴随：

\[
\text{Context Length} \uparrow
\]

以及：

\[
\text{Cost} \uparrow,
\qquad
\text{Latency} \uparrow
\]

同时无关信息也可能增加。

因此 Agent 需要：

\begin{itemize}
    \item Retrieval（检索）；
    \item Summarization（总结）；
    \item Compression（压缩）；
    \item Forgetting（遗忘）。
\end{itemize}

\begin{notebox}
不要把 Memory 简化成：

“把所有聊天历史全部塞进 Prompt”。

Memory 真正涉及的问题是：

\begin{itemize}
    \item What to remember?
    \item What to retrieve?
    \item What to forget?
    \item When to summarize?
\end{itemize}

这些本身也是 Agent Research 的重要问题。
\end{notebox}

% ============================================================
% 10. Planning
% ============================================================

\section{Step 7：Planning——复杂任务如何规划}

\begin{outlinebox}
这一部分展示：

\begin{enumerate}
    \item Planning（规划）的意义；
    \item ReAct；
    \item Plan-and-Execute；
    \item Research Task 的 Plan 示例。
\end{enumerate}
\end{outlinebox}

如果 Agent 每次只考虑：

\[
\text{下一步做什么？}
\]

对于 Long-Horizon Task（长时程任务）
可能容易出现方向漂移。

因此可以显式加入 Planning。

\subsection{ReAct}

ReAct 可以简化理解为：

\[
\text{Reason}
\rightarrow
\text{Act}
\rightarrow
\text{Observe}
\rightarrow
\text{Reason}
\]

即：

\[
\text{Reasoning}
+
\text{Acting}
\]

但现代系统不一定会把内部 Reasoning
显式打印出来。

核心不是有没有显示 Thought，
而是：

\[
\text{Decision}
\leftrightarrow
\text{Environment Feedback}
\]

\subsection{Plan-and-Execute}

另一种思路是先生成 Plan。

例如：

\begin{enumerate}
    \item 定义研究范围；
    \item 生成搜索关键词；
    \item 搜索论文；
    \item 筛选论文；
    \item 提取 Method / Dataset / Result；
    \item 按技术路线分类；
    \item 找出缺失方向；
    \item 再次搜索；
    \item 生成报告。
\end{enumerate}

然后 Executor（执行器）逐步完成任务。

关键是：

\begin{center}
Plan 也可以根据 Observation 动态修改。
\end{center}

这就是 Re-planning（重新规划）。

\begin{notebox}
这里不建议展开 Tree of Thoughts、
Monte Carlo Tree Search 等高级 planning 方法。

因为 Workshop 的目标是“搭 Agent”，
而不是做 Agent Planning Survey。
\end{notebox}

% 11. Reflection
% ============================================================

\section{Step 8：Reflection 与 Critic}

\begin{outlinebox}
这一部分展示：

\begin{enumerate}
    \item 为什么一次生成不够可靠；
    \item Critic（评审模块）；
    \item Environment Feedback（环境反馈）；
    \item Coding Agent；
    \item Writing Agent。
\end{enumerate}
\end{outlinebox}

最简单的生成流程是：

\[
\text{Generate}
\rightarrow
\text{Finish}
\]

更强的 Agent 可以：

\[
\text{Generate}
\rightarrow
\text{Evaluate}
\rightarrow
\text{Revise}
\]

\subsection{Coding Agent}

Coding 场景尤其适合 Agent。

\begin{center}

\begin{tikzpicture}[node distance=0.65cm]

\node[box] (g) {Generate Code};
\node[box, right=of g] (r) {Run Tests};
\node[box, right=of r] (e) {Observe Error};

\node[box, below=1cm of e] (a) {Analyze};
\node[box, left=of a] (m) {Modify};

\draw[arrow] (g) -- (r);
\draw[arrow] (r) -- (e);
\draw[arrow] (e) -- (a);
\draw[arrow] (a) -- (m);
\draw[arrow] (m) -| (r);

\end{tikzpicture}

\end{center}

环境可以提供明确反馈：

\begin{itemize}
    \item Syntax Error；
    \item Compiler Error；
    \item Runtime Error；
    \item Unit Test Failure。
\end{itemize}

因此 Agent 可以：

\[
\text{写代码}
\rightarrow
\text{运行}
\rightarrow
\text{观察错误}
\rightarrow
\text{修改}
\]

\subsection{Writing Agent}

论文写作也可以类似：

\[
\text{Draft}
\rightarrow
\text{Critique}
\rightarrow
\text{Verify}
\rightarrow
\text{Revise}
\]

Critic 可以检查：

\begin{itemize}
    \item Logical Consistency；
    \item Citation；
    \item Missing Evidence；
    \item Writing Quality。
\end{itemize}

但需要强调：

\begin{center}
\textbf{LLM Critic 并不天然可靠。}
\end{center}

真正更有价值的是
Verifiable Feedback（可验证反馈）。

例如：

\begin{itemize}
    \item Unit Test；
    \item Compiler；
    \item Calculator；
    \item Database；
    \item Retrieved Source。
\end{itemize}

\begin{notebox}
这里可以举 Claude Code、Codex 等 Coding Agent
作为现实产品例子。

但仍然只讨论其公开可观察行为：

读取文件、修改代码、执行命令、读取错误、继续修改。

不要推断它们内部完整实现。
\end{notebox}

\section{Step 9：Multi-Agent}

\begin{outlinebox}
这一部分控制在 3--4 分钟。

展示：

\begin{enumerate}
    \item Multi-Agent（多智能体）是什么；
    \item Manager--Worker；
    \item Role Specialization；
    \item 为什么“多调用几次 LLM”不等于 Multi-Agent。
\end{enumerate}
\end{outlinebox}

一个典型结构：

\begin{center}

\begin{tikzpicture}[node distance=1cm]

\node[box] (manager) {Manager};

\node[box, below left=1.2cm and 2cm of manager]
(research)
{Researcher};

\node[box, below=1.2cm of manager]
(coder)
{Coder};

\node[box, below right=1.2cm and 2cm of manager]
(review)
{Reviewer};

\node[box, below=1.2cm of coder]
(output)
{Final Output};

\draw[arrow] (manager) -- (research);
\draw[arrow] (manager) -- (coder);
\draw[arrow] (manager) -- (review);

\draw[arrow] (research) -- (output);
\draw[arrow] (coder) -- (output);
\draw[arrow] (review) -- (output);

\end{tikzpicture}

\end{center}

Multi-Agent 比较有意义的场景：

\begin{itemize}
    \item Role Specialization（角色专业化）；
    \item Information Isolation（信息隔离）；
    \item Parallel Execution（并行执行）；
    \item Independent Verification（独立验证）。
\end{itemize}

如果三个 Agent：

\begin{itemize}
    \item 使用相同模型；
    \item 拿到完全相同 Context；
    \item 使用相同 Prompt；
    \item 做完全相同任务；
\end{itemize}

那么它可能只是：

\[
\text{把 LLM 调用三次}
\]

而不是结构上真正有价值的 Multi-Agent。

\section{Step 10：什么时候才需要 Agent Framework}

\begin{outlinebox}
这一部分展示：

\begin{enumerate}
    \item 为什么简单的 while loop 不够；
    \item Framework 解决的 Engineering Problem；
    \item LangGraph；
    \item OpenAI Agents SDK；
    \item 为什么学习 Agent 不应该从框架开始。
\end{enumerate}
\end{outlinebox}

我们前面的最小 Agent：

\begin{lstlisting}[language=Python]
while not done:

    action = llm(state)

    result = execute(action)

    update(state, result)
\end{lstlisting}

已经包含了 Agent 的核心机制。

但真正系统还需要：

\begin{itemize}
    \item State Management；
    \item Retry；
    \item Timeout；
    \item Checkpoint；
    \item Persistence；
    \item Logging；
    \item Tracing；
    \item Human-in-the-loop；
    \item Parallel Execution；
    \item Permission Control；
    \item Error Recovery。
\end{itemize}

这才是 Agent Framework 的主要意义。

可以把 Framework 理解成：

\[
\text{Agent Logic}
+
\text{Engineering Infrastructure}
\]

常见工具包括：

\begin{itemize}
    \item LangGraph；
    \item OpenAI Agents SDK；
    \item LangChain；
    \item AutoGen；
    \item CrewAI。
\end{itemize}

\begin{keybox}
学习顺序建议是：

\[
\text{自己写最小 Agent Loop}
\]

然后：

\[
\text{理解 State / Tool / Planning}
\]

最后才：

\[
\text{学习 Framework}
\]

而不是反过来。
\end{keybox}

\begin{notebox}
Agent Framework 更新速度非常快。

Workshop 不要花时间教：

“某个框架某个 API 参数怎么写”。

半年以后 API 可能已经变化。

真正长期有效的是：

\begin{itemize}
    \item Tool；
    \item State；
    \item Agent Loop；
    \item Planning；
    \item Feedback；
    \item Evaluation。
\end{itemize}
\end{notebox}

% ============================================================
% 14. Failure
% ============================================================

\section{Agent 为什么容易失败？}

\begin{outlinebox}
这一部分用于避免 Workshop 变成单纯“宣传 Agent”。

主要展示：

\begin{enumerate}
    \item Error Accumulation；
    \item Tool Error；
    \item Infinite Loop；
    \item Context Growth；
    \item Cost；
    \item Evaluation。
\end{enumerate}
\end{outlinebox}

\subsection{Error Accumulation}

假设为了简单说明，
每一步成功概率都是：

\[
p = 0.95
\]

并且假设不同步骤之间独立。

那么 20 步全部成功的概率：

\[
p^{20}
=
0.95^{20}
\approx
0.36
\]

这说明 Long-Horizon Task
很容易发生误差累积。

但需要明确：

\begin{quote}
现实 Agent 中不同步骤并不独立，
这个计算只是直观示例。
\end{quote}

\subsection{常见 Failure Mode}

包括：

\begin{itemize}
    \item Wrong Tool；
    \item Wrong Arguments；
    \item Misread Observation；
    \item Goal Drift；
    \item Infinite Loop；
    \item Context Explosion；
    \item Excessive Cost。
\end{itemize}

因此系统通常必须设置：

\begin{lstlisting}[language=Python]
MAX_STEPS = 20

TIMEOUT = 300

TOKEN_BUDGET = ...

COST_BUDGET = ...

ALLOWED_TOOLS = [...]
\end{lstlisting}

并加入：

\begin{itemize}
    \item Sandbox；
    \item Permission Control；
    \item Input Validation；
    \item Human Approval；
    \item Logging / Tracing。
\end{itemize}

\begin{keybox}
Autonomous（自主）

并不意味着

Uncontrolled（不受控制）。
\end{keybox}

\section{Agent 应该如何评价？}

不能只看：

\begin{quote}
“最终回答看起来不错。”
\end{quote}

至少应该评价：

\begin{itemize}
    \item Task Success Rate（任务成功率）；
    \item Tool-call Accuracy（工具调用准确率）；
    \item Planning Quality（规划质量）；
    \item Robustness（鲁棒性）；
    \item Number of Steps（执行步数）；
    \item Token Usage；
    \item Latency（延迟）；
    \item Monetary Cost（实际成本）。
\end{itemize}

对于科研而言，还有一个非常重要的问题：

\[
\text{Performance Gain}
=
?
\]

提升究竟来自：

\[
\text{Stronger LLM}
\]

还是：

\[
\text{Better Agent Architecture}
\]

这也是 Agent Research 中值得研究的问题。

\section*{最后建议}

如果一个同学明天准备自己搭一个 Agent，
最推荐的学习路线是：

\begin{enumerate}
    \item 写通一个 LLM API；
    \item 让模型返回 Structured Output；
    \item 写两个简单 Tool；
    \item 手写一个 Agent Loop；
    \item 加 State；
    \item 加 Memory；
    \item 加 Planning；
    \item 加 Feedback；
    \item 最后再学习 LangGraph 等 Framework。
\end{enumerate}

最后可以用一句话结束：

\begin{quote}
如果以后看到任何新的 Agent 系统，
先把它拆开看：

模型是什么？

工具是什么？

状态在哪里？

谁决定下一步？

循环如何停止？

拆完以后，大部分 Agent 系统其实没有那么神秘。
\end{quote}
