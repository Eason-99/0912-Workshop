# S0–S7 数据流与模块调用说明

本文说明每个 Stage 的数据从哪里进入、由谁控制、经过哪些文件和主要函数，以及最终写出什么产物。本文是教学与维护文档，首次使用：S0。

## 1. 所有 Stage 共用的启动链路

用户始终只执行：

```bash
python src/run.py
```

公共启动数据流如下：

```text
src/config.yaml + src/core/.env
  → run.py: main()
  → core/config.py: load_config()
      → _validate_config()
      → load_dotenv(core/.env)
      → AppConfig
  → core/config.py: validate_stage_environment()
  → core/recorder.py: create_run_id() / Recorder()
  → core/model.py: OpenAIModel()
  → core/context.py: ExecutionContext()
  → [仅 S2+] core/runtime.py: build_tool_registry()
  → run.py: _load_runner()
  → stages/<当前 stage>.py: run()
  → Recorder.write_json("result.json")
```

各公共节点的职责：

| 文件 | 主要函数或对象 | 输入 | 输出或副作用 | 首次使用 |
| --- | --- | --- | --- | --- |
| `config.yaml` | 单一非敏感配置 | 人工编辑的运行参数与 active profile | Stage、任务、模型名称、搜索、PPT 和限制参数 | S0 |
| `core/.env` | 本机私密配置 | 人工填写的 URL 与 Key | 当前模型连接和 Tavily 凭据；被 Git 忽略 | S0 |
| `run.py` | `main()` | 固定配置路径 | 初始化一次运行并分派 Stage | S0 |
| `core/config.py` | `load_config()` | YAML 路径 | 校验配置、加载 `.env`，返回 `AppConfig` | S0 |
| `core/config.py` | `active_model_profile()` / `model_connection()` | `AppConfig` | 选择 DeepSeek/第三方并读取其 URL + Key | S0 |
| `core/config.py` | `validate_stage_environment()` | `AppConfig` | 检查模型连接、工具能力和 Tavily Key | S0 |
| `core/recorder.py` | `Recorder` | 运行目录、Stage | `events.jsonl`、`model_calls.jsonl` 和逐轮原始文件 | S0 |
| `core/model.py` | `OpenAIModel` | 模型配置、Recorder | 统一模型调用接口 | S0 |
| `core/context.py` | `ExecutionContext` | 配置、Recorder、运行目录 | 本次运行的来源、证据、Deck、State、Plan | S0 |
| `core/runtime.py` | `build_tool_registry()` | `AppConfig` | 完整工具注册表；各 Stage 只暴露允许的子集 | S2 |

`run.py: main()` 会在执行阶段前创建：

```text
src/runs/<run_id>/
  config.snapshot.yaml
  events.jsonl
  model_calls.jsonl
  model_calls/
    model_call_001_request.json
    model_call_001_output.txt
    model_call_001_response.json
  result.json
  ...当前 Stage 的其他产物
```

若配置或密钥校验失败，不调用模型或工具；若 Stage 运行失败，错误写入 `result.json` 和 `events.jsonl`。

`model_calls.jsonl` 是所有 Stage 共用的模型轮次索引。S0 只有 `model_call_001`；后续多轮调用依次使用 `model_call_002`、`model_call_003`。每个成功调用对应 request/response 两条记录，失败调用对应 request/error 两条记录，因此即使 API 失败，最终 Prompt 仍已在请求发出前落盘。

## 2. 核心数据对象如何流动

| 数据对象 | 定义位置 | 生产者 | 主要消费者 | 首次使用 |
| --- | --- | --- | --- | --- |

## 3. S0：普通 API

### 控制权

宿主代码只调用模型一次。模型不具备工具，也没有结构化输出约束。

### 数据链路

```text
config.task
  → core/prompts.py: task_prompt()
  → stages/s0_api.py: run()
  → core/model.py: OpenAIModel.generate_text()
      → OpenAIModel._create()
      → Recorder.record_model_request() / model_calls.jsonl: phase=request
      → OpenAI-compatible Responses API（流式接收）
      → Recorder.record_model_response() / model_calls.jsonl: phase=response
      → model_calls/model_call_001_output.txt（原始 output_text）
  → 原始文本 draft（不执行 strip）
  → core/recorder.py: Recorder.write_text("draft.md")
  → run.py: Recorder.write_json("result.json")
```

### 主要文件和函数

- `stages/s0_api.py: run()`：组装任务，发起一次自由文本请求并保存草稿。
- `core/prompts.py: task_prompt()`：把 `config.task` 转换成完整中文任务。
- `core/model.py: generate_text()`：返回未裁剪的原始 `response.output_text`，仅用 `strip()` 判断是否为空。
- `core/model.py: _create()`：统一应用 active profile、模型名、输出 Token 上限、调用次数和日志策略。
- `core/recorder.py: write_text()`：生成 `draft.md`。
- `core/recorder.py: record_model_request()`：调用前保存最终 payload，确保失败请求也可复盘。
- `core/recorder.py: record_model_response()`：保存原始文本、完整 SDK 响应及统一调用索引。

### 产物

`draft.md`、`model_calls.jsonl`、`model_calls/model_call_001_*`、`events.jsonl`、`config.snapshot.yaml`、`result.json`。本阶段不会生成 JSON Deck 或 PPT。

## 4. S1：Structured Output

### 控制权

宿主代码仍只调用模型一次，但要求模型输出严格 `DeckSpec`。本阶段到 JSON 为止，不调用 PPT 工具。

### 数据链路

```text
config.task
  → task_prompt() + deck_instructions()
  → stages/s1_structured.py: run()
  → core/contracts.py: deck_schema(slide_count)
  → core/model.py: OpenAIModel.generate_structured()
      → OpenAIModel._create(text.format=json_schema)
      → json.loads(ModelTurn.output_text)
  → core/contracts.py: validate_deck()
  → Recorder.write_json("deck.json")
```

### 主要文件和函数

- `core/contracts.py: deck_schema()`：规定标题、五页、稳定 ID、bullets、source_ids 和备注字段。
- `core/model.py: generate_structured()`：向 Responses API 传入严格 JSON Schema 并解析返回值。
- `core/contracts.py: validate_deck()`：再次在本地检查页数和 `s1`–`s5` 顺序。
- `stages/s1_structured.py: run()`：只保存 `deck.json`，明确不执行 `create_ppt`。

### 产物

`deck.json`、`events.jsonl`、`result.json`。运行目录中不应出现 `.pptx`。

## 5. S2：Tool Calling

### 控制权

S2 有两个固定教学回合。宿主代码决定何时开始和结束回合；模型只决定唯一可用工具的调用参数。因此这是 Tool Calling，还不是自主 Agent Loop。

### 公共 Tool Calling 链路

```text
prompt + 当前回合允许的工具名
  → core/runtime.py: run_tool_round()
  → ToolRegistry.schemas()
  → core/model.py: start_tool_turn()
  → OpenAIModel.extract_tool_calls()
  → core/runtime.py: execute_call()
      → ToolRegistry.execute()
      → _validate_schema_value()
      → 对应 handler / tools 模块
  → ToolResult
  → core/runtime.py: tool_output_item(function_call_output, call_id, output)
  → core/model.py: continue_tool_turn(previous_response_id, function outputs)
  → 模型最终摘要
```

### 回合 A：搜索工具

```text
stages/s2_tools.py: run()
  → run_tool_round(..., ["search_web"])
  → core/runtime.py: _search_handler()
  → tools/research.py: search_web()
  → Tavily API
  → 候选 Source 列表，status=candidate_only
  → ExecutionContext.sources
  → ExecutionContext.persist_sources()
  → sources.json
```

搜索摘要只是候选信息，不可直接作为数字证据。

### 回合 B：PPT 工具

```text
stages/s2_tools.py: run()
  → run_tool_round(..., ["create_ppt"])
  → core/runtime.py: _create_ppt_handler()
      → _validate_schema_value()
      → core/contracts.py: validate_deck()
      → 检查 source_id 是否已经 read_page
  → tools/presentation.py: create_ppt()
      → _add_textbox()
      → python-pptx
  → deck_v1.json / deck_v1.pptx / 稳定文件名 PPT
```

S2 没有读页步骤，因此示例 Deck 应不引用外部来源，并说明没有完成充分调研。

### 产物

`sources.json`、`deck_v1.json`、`deck_v1.pptx`、配置指定的稳定文件名、`tool_round_summaries.md` 和工具事件。

## 6. S3：固定 Workflow

### 控制权

Python 代码预先决定搜索、读页、证据抽取、写作和 PPT 生成的顺序。模型只能完成局部选择与生成，不能改变整体路径。

### 数据链路

```text
stages/s3_workflow.py: run()
  → stages/common.py: run_fixed_workflow()
  → _host_call("search_web", 排名查询)
  → ranking results
  → selection_prompt()
  → OpenAIModel.generate_structured(product_selection_schema)
  → validate_products()
  → products[5–6]

对每个 product 执行固定的两类查询：
  → _host_call("search_web", MAU 查询)
  → _host_call("read_page", 第一条候选 URL)
  → _host_call("search_web", 定位/功能查询)
  → _host_call("read_page", 第一条候选 URL)

全部来源：
  → compact_sources()
  → evidence_prompt()
  → OpenAIModel.generate_structured(evidence_bundle_schema)
  → ExecutionContext.evidence
  → persist_evidence() / open_questions.json
  → build_comparability_report()
      → evidence_is_comparable()
      → comparability.json

Evidence + 可比性报告 + 已读 Source：
  → deck_instructions()
  → OpenAIModel.generate_structured(deck_schema)
  → validate_deck()
  → _host_call("create_ppt")
  → PPT
```

### 主要文件和函数

- `stages/common.py: _host_call()`：把代码选定的动作包装成带 `host_XXX` ID 的工具调用。
- `tools/research.py: read_page()`：首次实际使用；下载 HTML、删除脚本样式并截断正文。
- `core/contracts.py: product_selection_schema()` / `validate_products()`：保证候选数量与唯一性。
- `core/contracts.py: evidence_bundle_schema()`：要求每条 Evidence 携带指标、时期、地区、终端和原文片段。
- `core/contracts.py: evidence_is_comparable()`：用确定性字段判断两条指标是否同口径。
- `stages/common.py: compact_sources()`：控制进入模型上下文的正文长度。
- `stages/common.py: build_comparability_report()`：把完整定量 Evidence 分组，把字段缺失项排除并说明原因。
- `stages/common.py: run_fixed_workflow()`：固定整个 Workflow，不根据资料缺口增加临时分支。

### 产物

`sources.json`、`evidence.json`、`comparability.json`、`open_questions.json`、`deck_v1.json`、PPT 和完整固定步骤事件。

## 7. S4：Agent Loop

### 控制权

模型根据每次 ToolResult/Observation 自主选择下一次 `search_web`、`read_page`、`create_ppt` 或结束。宿主只限制工具集合、步数、调用次数和总时长。

### 数据链路

```text
stages/s4_agent.py: run()
  → stages/common.py: run_research_agent(enable_plan=False)
  → core/runtime.py: run_agent_loop()

循环：
  agent_instructions(state=None, plan=None)
  → OpenAIModel.start_tool_turn() 或 continue_tool_turn()
  → extract_tool_calls()
  → execute_call()
  → search_web / read_page / create_ppt
  → ToolResult
  → tool_output_item()
  → 使用 call_id 返回模型
  → 下一轮

无 ToolCall：
  → 已生成 PPT：AgentOutcome(status="completed")
  → 未生成 PPT：AgentOutcome(status="incomplete")
达到限制或异常：
  → limit_reached / error
```

### 与 S3 的关键区别

S3 的下一步由 `run_fixed_workflow()` 中的 Python 顺序决定；S4 的下一步来自每轮模型返回的 `ToolCall`。工具函数本身完全复用。

### 产物

动态 `events.jsonl`、`sources.json`、模型最终调用 `create_ppt` 后产生的 Deck/PPT，以及包含结束状态的 `result.json`。

## 8. S5：显式 State

### 控制权

工具选择仍由 S4 的 Agent Loop 完成；S5 新增由 runtime 维护的可信 `TaskState`，并在每轮模型调用前注入最新状态。

### 数据链路

```text
stages/s5_state.py: run()
  → stages/common.py: make_task_state()
  → TaskState(goal, metric_scope, ...)
  → ExecutionContext.persist_state()
  → state.json
  → run_research_agent(enable_plan=False)

每次工具执行：
  execute_call()
  → _record_tool_result()
  → 更新 current_step
  → 成功：completed_actions / source_ids
  → 失败：open_questions
  → persist_state()

每次模型调用前：
  instructions_factory()
  → TaskState.to_dict()
  → agent_instructions(state=<最新状态>)
  → run_agent_loop()

循环结束：
  → _finish_state()
  → termination_reason
  → state.json
```

`current_deck` 只有在 `_create_ppt_handler()` 实际成功后才更新，模型仅声称“已完成”不会改变该字段。

### 产物

S4 的全部产物，外加持续更新的 `state.json`。

## 9. S6：Planning 与 Re-planning

### 控制权

S6 复用 S5 的 State，并在 Agent Loop 之前生成显式计划。模型可根据 Observation 调用 `update_plan`；runtime 负责校验和保存版本历史。

### 初始计划链路

```text
stages/s6_planning.py: run()
  → make_task_state() / persist_state()
  → stages/common.py: create_initial_plan()
  → core/prompts.py: planning_prompt()
  → OpenAIModel.generate_structured(plan_schema)
  → core/contracts.py: PlanState(items, revision=1)
  → ExecutionContext.persist_plan()
  → plan.json
```

### Agent 与 Re-plan 链路

```text
run_research_agent(enable_plan=True)
  → allowed tools += update_plan
  → instructions_factory()
      → TaskState.to_dict()
      → PlanState.to_dict()
      → agent_instructions(state, plan)
  → run_agent_loop()

模型发现原计划不再成立：
  → ToolCall(name="update_plan", items, reason)
  → execute_call()
  → _update_plan_handler()
  → PlanState.replace()
      → 旧版本进入 history
      → revision + 1
      → 保存 change_reason
  → persist_plan()
  → ToolResult 返回模型
```

### 产物

S5 的全部产物，外加包含初始版本、当前版本、变更原因和历史版本的 `plan.json`。

## 10. S7：Reflection

### 控制权

S7 先复用 S6 得到初版 PPT，再由代码触发确定性检查；模型根据 `ReviewIssue` 决定具体页面修订内容。检查与重建次数受 `max_review_rounds` 限制。

### 初版与检查链路

```text
stages/s7_reflection.py: run()
  → make_task_state()
  → create_initial_plan()
  → run_research_agent(enable_plan=True)
  → 初版 deck_v1.pptx
  → _review_current_version()
      → tools/presentation.py: render_ppt()
          → LibreOffice: PPTX → PDF
          → pdftoppm: PDF → PNG
          → 缺少程序时返回 rendered=false，不伪造成功
      → tools/review.py: check_deck()
          → bullets/字数/来源/份额标签
          → check_ppt_bounds()
      → review_v1.json
```

### 修订循环

```text
ReviewIssue[]
  → core/prompts.py: reflection_prompt(deck, issues)
  → core/runtime.py: run_tool_round(..., ["patch_deck"])
  → 模型 ToolCall(name="patch_deck")
  → _patch_deck_handler()
  → tools/presentation.py: patch_deck()
  → core/contracts.py: apply_deck_patches()
  → 更新 ExecutionContext.deck
  → _create_revised_ppt()
  → execute_call("create_ppt")
  → deck_v2.json / deck_v2.pptx
  → _review_current_version()
  → review_v2.json
  → 无问题或达到 max_review_rounds 后结束
```

### 主要检查规则

- `tools/review.py: check_deck()`：检查每页 bullet 数、字符数、未知来源 ID、无来源数字和“样本内 MAU 份额”标签。
- `tools/review.py: check_ppt_bounds()`：读取实际 PPTX，检查 shape 是否超出画布。
- `tools/presentation.py: render_ppt()`：负责视觉产物生成；缺少 LibreOffice/pdftoppm 时降级，不影响结构规则检查。
- `core/contracts.py: apply_deck_patches()`：只允许通过稳定页面 ID 做整页替换，避免位置索引漂移。

### 产物

S6 的全部产物，外加 `render_vN.json`、`slides_vN/`（渲染工具可用时）、`review_vN.json`、`deck_patch_N.json` 和修改前后的多个 Deck/PPT 版本。

## 12. 教学时最重要的控制权变化

| 对比 | 数据链路没有改变的部分 | 真正改变的部分 |
| --- | --- | --- |
| S0 → S1 | 都经过同一个 `OpenAIModel` | 文本输出变为严格 `DeckSpec` |
| S1 → S2 | `DeckSpec` 契约继续复用 | 新增 ToolCall → runtime → ToolResult |
| S2 → S3 | 搜索和 PPT 工具继续复用 | 多步骤顺序由 Python Workflow 固定 |
| S3 → S4 | 同一个 ToolRegistry 和工具函数 | 下一步由模型根据 Observation 决定 |
| S4 → S5 | Agent Loop 不变 | 执行事实进入显式 `TaskState` 并回注 Prompt |
| S5 → S6 | State 和 Agent Loop 不变 | 新增可观察、可版本化的 Plan/Re-plan |
| S6 → S7 | 调研、计划和 PPT 工具不变 | 外部 ReviewIssue 进入修订和复查循环 |

因此，判断一个阶段新增了什么，应该观察“数据多经过了哪个契约或模块”以及“下一步动作的控制权发生了什么变化”，而不是只看最终是否生成 PPT。
